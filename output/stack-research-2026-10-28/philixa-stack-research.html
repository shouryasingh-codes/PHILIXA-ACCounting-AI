Research completed from official public documentation and current local source. No vendor trial or new accuracy benchmark was run. Application code/configuration was not changed by this research.

Overview

Best fit for Philixa is a controlled accounting agent over synchronised business data, not a bigger chatbot. Keep the current backend, add reliable context tools and a durable evidence loop, then benchmark one document-understanding upgrade. This is a project-specific engineering recommendation, not a claim that one universal best stack exists.

Facts versus inference: product capabilities below are documented by vendors. Proposed stack choices are our engineering judgement. Private competitor model/framework details remain unknown unless explicitly disclosed.

Competitors

Tally Docs by Ira

Direct competitor: Indian Tally invoice entry

Published capability: Reads documents into draft vouchers; maps masters; user reviews before posting.

Public architecture evidence: FAQ documents master matching and saved mappings. Underlying model/framework stack is not disclosed in the reviewed sources.

Philixa implication — inference: OCR-to-voucher is already a native product category. Compete on measured reduction in review effort, not feature novelty.

Limits / do not overclaim: FAQ lists English invoices and one transaction per file; source quality/layout issues can require correction. Eligibility depends on license/TSS/release.

Cost reality — illustrative, not a bill

Mistral lists $4 per 1,000 OCR pages or $5 per 1,000 annotated pages. At the annotated rate, 100 single-page documents cost $0.50 for that service, assuming one pass and standard listed pricing. Other model calls, retries, taxes, storage and hosting are additional.

Groq lists GPT-OSS 20B at $0.075 input / $0.30 output and 120B at $0.15 input / $0.60 output per million tokens. At an assumed 2,000 input + 500 output tokens per call, 1,000 calls would be $0.30 or $0.60 respectively. This is arithmetic from list prices, not measured Philixa usage or a free-tier promise. A multi-step task can involve several calls. Local OCR has no per-page external API charge, but consumes hardware, memory, power and maintenance.

What peers actually do

The recurring public pattern is ingestion, structured extraction, master/history matching, deterministic/business checks, exception routing and an ERP connector. Some vendors use proprietary training; others expose rules and approved mappings. These sources do not prove that competitors use LangGraph, Groq, PaddleOCR or our proposed stack.

Bill-free chat

For “Sharma se 50 Cement bags liye”, read the selected company, approved supplier/item identity, unit, effective tax configuration, recent matching purchases and duplicate evidence. Historical rate is a labelled proposal, not evidence of today’s actual rate. Offer one review of material assumptions. If no source contains invoice reference/date or transaction facts, ask for those together; no technology can recover facts that were never supplied or recorded.

Evidence contract

Every field should carry value, source type, native/source identity, source date, observed_at, draft revision and confirmed/proposed/unresolved status. Precedence: explicit current user correction or source evidence, validated effective masters for master facts, approved alias for identity, history for suggestions. Contradictions create an exception; they must not silently overwrite current evidence. Retrieval must enforce workspace/company permissions server-side.

Memory without training

Use relational memory for supplier IDs, item IDs, effective master versions and approved aliases. Exact keys first; fuzzy/embedding search only proposes candidates. Do not feed all database rows into every prompt or allow unrestricted model-generated SQL. pgvector can later help semantic document search; it is not needed to compute balances, choose tax ledgers or identify duplicates.

Autonomy boundary

Read tools can gather evidence within permission scopes. Validation issues route to review/block. Posting requires a specific reviewed action or an enabled durable policy, rechecked at dispatch. Graph checkpoints help resume reasoning; action identity/outbox/helper journal prevent blind re-posting. Closed Tally/PC means stale cached reads and queued work, not a live connection to a stopped accounting application.

Deployment

Keep the paired outbound connector for customer PCs. Official Tally XML/JSON/ODBC routes exist; WebSocket bridging is a documented reference pattern, not a Tally-hosted service. A protocol migration should be separately certified against supported releases. ngrok is a temporary demo exposure, not persistent product hosting; a stable HTTPS backend and managed secrets/backup/update process are later pilot deployment work.

Tally integration formats · Tally WebSocket reference

What not to add now

No custom foundation-model training, mandatory vector database, multiple autonomous agents, simultaneous OCR vendors, Kubernetes or Temporal migration just to claim intelligence. Temporal is a credible durable workflow alternative when long-running orchestration justifies its operational cost; it does not remove connector idempotency requirements.

Accuracy and release

Measure extraction, entity mapping, accounting and native posting separately, then end-to-end. Retain unreadable/unsupported cases in denominators. Split every copy of a bill together to prevent leakage. Existing project gate requires 200 accountant-labelled representative real invoices including 100 held-out, zero observed critical errors in eligible auto-post cases, plus measured review-inclusive handling time. These are project rollout requirements, not proof or a universal guarantee; real-world accuracy remains unverified.

Execution order

1. Establish a frozen chat+bill baseline with expected outcomes. 2. Build native Tally context tools/read models and field provenance. 3. Add multi-field understanding and a compact proposal. 4. Add checkpoints and bounded tool/validation loop. 5. Compare one local document parser and an optional paid challenger under identical tests. 6. Run shadow mode and accountant evaluation before controlled posting rollout.

Positioning

Say: Philixa is being built to reduce the work between a task and a verified Tally result. Do not claim unique OCR, fully automatic accounting, 100% accuracy or 50% savings yet. Clarify with an accountant which workflow causes the most repeated corrections; prove handling time against the same workload including review and failures.
